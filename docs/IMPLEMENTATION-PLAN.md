분석한 결과다. **로컬 Claude Code 세션(이 워크트리 안)이 `GO` 지시를 받으면 이

- 체크인 화면 좌표(ui-spec-check) 24건 중 23건 PASS. 헤더 워드마크 폭 0.59px 차이는 이번 변경 전부터 있던 글꼴 렌더링 차이(헤더 미수정).
- 확인 필요: SIMULATION.md 4장 공식으로 +1,500kcal의 t=24h 표시체중은 약 2.45kg이라 5장 "다음 날 +1~2kg"과 어긋난다(보통 1,000kcal는 약 1.7kg). 화면은 공식 계산값을 그대로 보여준다. 상수·공식 조정 여부는 사용자 결정 필요.
- 홈 "오늘의 상태" 6개 카드(칼로리·물·활동·식단·체중·컨디션)는 앱이 모으는 데이터가 없어 샘플로 남겼다.
- 10단계(P2)는 착수하지 않음.
- main의 calorie-engine(몸 정보 온보딩·TDEE)을 병합하며 몸 정보를 프로필에 저장하도록 연결했다. 다만 SIMULATION.md 4-B(여러 이벤트 합산·글리코겐/나트륨 각 2kg 상한)는 아직 엔진에 없다 — 지금은 이벤트마다 4-A 단독 계산. 다음 작업 후보.

## 0. 조건
- 무료 API / 무료 티어 / 결제 없는 방법만 사용한다 (사용자 지시, 2026-09-24).
- 이 조건은 `docs/LLM.md`의 "LLM 공급자: Anthropic Claude API [확정]"과
  **충돌한다** — Anthropic API는 신용카드 없이 쓸 수 있는 영구 무료 티어가
  없다. 아래 1장에서 대안을 제시한다. 구현 시작 전에 `docs/LLM.md`의 해당
  줄을 갱신할 것(CLAUDE.md 작업 규칙: "프로젝트 방향이 바뀌면 문서를
  업데이트한다").

## 1. LLM 공급자 — 제안: 템플릿 우선 + 무료 티어 선택적 연동
- **기본(디폴트, 항상 동작)**: 실제 LLM 호출 없이, 계산된 수치(초과kcal·비율·
  실제지방·수렴시간 등)를 입력으로 받아 `docs/LLM.md` 2~4장의 안전 규칙을
  반영한 **고정 템플릿 문구**를 조합해서 반환한다. `sample.ts`의
  `SIM_SAMPLE`/`GRAPH_POINTS`/`GUIDE_SAMPLE` 문구가 이미 이 형태(계산값을
  문장에 끼워 넣는 방식)라 그대로 패턴을 확장하면 된다. 비용 0원, 로그인 불필요,
  항상 동작 — 데모 안정성 최우선이라는 LLM.md의 "폴백" 요구사항과도 일치.
- **선택(있으면 사용)**: `/api/coach`에서 환경변수(`COACH_LLM_PROVIDER`,
  `COACH_LLM_API_KEY`)가 설정된 경우에만 실제 LLM을 호출하고, 없거나 실패하면
  위 템플릿으로 자동 폴백한다. 후보(2026-09 기준 무료 티어, 카드 불필요로
  확인됨):
  - **Groq** — 분당 30요청 / 일 1,000요청 / 일 200K 토큰. 속도 빠름, 데이터
    학습 활용 관련 별도 caveat 없음. 1순위 추천.
  - **Google AI Studio (Gemini)** — 분당 5~15 / 일 20~1,500(모델별 상이),
    Gemini/Gemma 8종. 무료 티어 프롬프트가 학습에 쓰일 수 있음(EU/UK/EEA
    외) — 개인정보 미포함 입력이라 LLM.md 규칙과는 상충 없음.
  - 둘 다 가입 후 API 키 발급이 필요해 **사용자가 브라우저에서 직접 로그인/
    가입해야 하는 단계**다. 그 키가 없어도 템플릿 폴백으로 앱은 끝까지
    동작하므로, 이 단계는 급하지 않으면 건너뛰어도 된다.
- 근거: OpenRouter 블로그·klymentiev.com 2026-09 비교 (무료/무카드 조건만
  필터링).

## 2. 기능별 판단

| 기능 | 판단 | 방법 / 비고 |
|---|---|---|
| 저장 모듈 (프로필·아바타·이벤트·시뮬결과·체크인) | **완전 가능** | `ARCHITECTURE.md`에 이미 localStorage 단독으로 확정. 접근을 한 모듈로 모아 구현. 비용 0, 로그인 불필요 |
| 이벤트 시뮬레이션 엔진 | **완전 가능** | `SIMULATION.md` 4장 공식·상수 그대로 순수 TS 함수로 구현. 외부 API 불필요. 5장 검증 예시로 단위 테스트 가능 |
| 온보딩(정보 입력+아바타 설정) → 저장 연결 | **완전 가능** | 화면은 이미 있음. 제출 시 저장 모듈에 쓰고 `/app`으로 이동하는 로직만 추가 |
| 홈(아바타·말풍선·주간 날씨 스트립·이벤트 카드) | **완전 가능** | "날씨"는 실제 기상이 아니라 몸 상태/컨디션 은유(DESIGN.md 확정). 이벤트~체크인 사이 진행도를 규칙으로 맑음/흐림/소나기에 매핑하면 됨. 외부 날씨 API 불필요 |
| 이벤트 등록 → 시뮬레이션 결과(이중 그래프) | **완전 가능** | 등록 폼 입력 → 시뮬레이션 엔진 → `WeekPlayer`/`DualGraph`(이미 구현된 화면)에 실제 계산값 연결 |
| 재개 체크인(준비도 체크 → 코칭 메시지) | **완전 가능** | 폼은 이미 있음. 코칭 문구는 1장의 템플릿(+선택적 LLM) |
| 일탈 리프레이밍 메시지 | **완전 가능** | 마찬가지로 템플릿 기반 |
| 기록(지난 이벤트 타임라인, P1) | **완전 가능** | localStorage에 쌓인 이벤트/체크인 나열 |
| "데모 데이터 불러오기" (P1) | **완전 가능** | 기존 `sample.ts` 값을 저장 모듈에 시드 |
| 데이터 초기화 (마이페이지) | **완전 가능** | localStorage 비우기 |
| 재도전 경험치화 (P2) | **완전 가능하나 후순위** | 저장된 이벤트/체크인 개수 기반 파생값. PRD 원칙상 시간 부족하면 P2부터 버림 |
| 아바타 꾸미기 (얼굴형·헤어·의상·소품 커스터마이징, P2) | **구현 어려움** | `DESIGN.md`: 해당 에셋이 아직 없음("선택지는 빈 타일"). 코드 문제가 아니라 디자인 에셋 부재 — 새 그림 제작 없이는 탭 UI만 만들고 "준비 중" 처리가 최선 |
| 아바타 표정·소지품 세부 반응 (P2) | **부분 가능** | 몽실이 WebGL 2.5D 엔진 자체는 이미 완성되어 있음(`components/ui/mongsil/`). 지금은 `?weather=` 쿼리 프리뷰로만 날씨를 바꾸는데, 이걸 홈 화면의 "날씨" 룰(위 항목)과 실제 이벤트 상태에 연결하는 배선 작업만 필요 |
| PWA "홈 화면에 추가" (P2) | **범위 밖** | PRD Non-goals. 서비스워커/오프라인 기능도 명시적으로 안 만듦 |

## 3. 구현 순서 (PRD 우선순위 그대로: P0 먼저, 끝나기 전 P1/P2 착수 안 함)

1. 저장 모듈 (`src/lib/storage.ts` 등 한 곳) — 8종 데이터, 클라이언트 전용
2. 시뮬레이션 엔진 (`src/lib/simulation.ts`) — SIMULATION.md 4장 공식 + 5장 예시로 자체 검증
3. 온보딩 → 저장 연결, `/app/*` 프로필 없으면 리다이렉트
4. 이벤트 등록 → 시뮬레이션 → 결과 화면(이미 만든 WeekPlayer/DualGraph/DayScrubber)에 실제 계산값 연결
5. 홈 화면 날씨/말풍선/이벤트 카드를 저장된 실데이터로 연결
6. 재개 체크인 폼 → 저장 → 코칭 메시지(템플릿)
7. `/api/coach` 라우트 (템플릿 우선, 무료 티어 키 있으면 사용) + `.env.example`
8. 마이페이지 데이터 초기화, "데모 데이터 불러오기"
9. (P0 완주 확인 후) P1: 기록 탭, 날씨 UI 다듬기
10. (P1 끝나면) P2: 경험치 표시, 시간 남으면 아바타 반응 배선 — 아바타 꾸미기 에셋은 범위 밖으로 유지

각 단계 끝날 때마다: 브라우저 390×844 뷰포트로 화면 확인 → 관련 있으면
`docs/ui-spec-check.js`/`docs/ui-lint.js` 실행 → 의미 있는 단위로 git commit.

## 4. 검증
- 시뮬레이션 엔진: SIMULATION.md 5장 예시(+1,500kcal → 실제지방 약 0.19kg,
  다음날 +1~2kg)를 스크립트/테스트로 고정 검증. 새 테스트 프레임워크 추가는
  보류하고(불필요한 의존성 금지 원칙) 우선 node 단순 assert 스크립트로 시작,
  필요해지면 그때 판단.
- 화면: 실기기 대신 브라우저 모바일 뷰포트(390×844)로 확인 (ARCHITECTURE.md
  방침).
- 매 기능 연결 후 전체 코어 플로우(스플래시→온보딩→홈→예보→이벤트등록→
  시뮬레이션결과→체크인→기록누적) 중 해당 구간이 실제로 이어지는지 수동
  확인.

## 5. 미확정 / 리스크
- LLM 공급자 최종 확정 필요(1장) — 템플릿 전용으로 갈지, Groq/Gemini 키를
  받아 실제 호출도 붙일지는 구현 중 재확인.
- localStorage는 브라우저/기기별이고 모바일 Safari 사생활 보호 모드에서
  제한될 수 있음(ARCHITECTURE.md에 이미 문서화된 한계, MVP로는 수용).
- 아바타 꾸미기는 에셋이 없어 코드로 해결 불가 — 새 그림이 생기기 전까지는
  범위에서 제외.
